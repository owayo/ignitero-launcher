# 2026-10-31 定期点検

検索の履歴照合をクエリごとのパス索引に変え、履歴50件・500アプリの `app` 検索のCPU時間を
19.75msから7.48msへ短縮した。負の使用回数が履歴の削除候補の比較を壊す不具合も修正した。
空クエリの復元方法の変更は、小規模な一覧で遅くなったため採用していない。

## 同期と依存

開始時の作業ツリーはクリーンで、未送信コミットもなかった。`origin/main` をfetchし、
`git pull --rebase` で変更がないことを確認した。開始時のHEADは `f15b82f`。
stashの作成・復元は不要だった。

`mise install` と `mise exec -- depup --install --include-pinned` を実行した。
Pythonを3.14.8から3.15.0へ更新し、mise.lockの書式2とmacOS arm64・x64の取得元・チェックサムを維持した。
`make emoji-keywords` はPython 3.15.0で成功し、生成辞書に差分はなかった。
CIの `minimum_release_age: 14d` はmise本体の導入条件で、Python成果物の経過日数を制限する設定ではない。

Swift依存はGRDB.swift 7.11.1、KeyboardShortcuts 3.1.0、fuse-swift 1.4.0、EmojiKit 3.1.0を維持した。
depupの検出と各公式リポジトリのリリース・タグを照合し、安定版の更新候補がないことを確認した。
fuse-swift 2.0.0-rc.1はプレリリースなので採用していない。

## 構造の調査と変更

astro-sightでSources内の42ファイルの構造を確認した。検索、キャッシュ再読込、スキャンの再実行、
外部プロセス実行、設定・履歴の読込を重点的に追った。差分にはcontext・impact・reviewを使用した。

採用した変更は `SearchService.applyHistoryBoost` の履歴の表現である。
従来は正規化済みタプル配列を結果ごとに完全一致・前方一致の順で走査していた。
新方式は履歴を1回正規化し、クエリに一致する履歴の先頭countを、一致種別ごとにパスで引ける辞書へ保存する。
照合処理を結果件数×履歴件数の走査から、履歴と結果それぞれの走査へ変えた。

完全一致の優先、同じ一致種別では先頭の履歴を使うこと、0や負数のcount、旧形式の未正規化キーワードの扱いは維持した。
公開APIと検索結果の補正式も変えていない。検索結果が空なら履歴の正規化自体を省く。

次の候補は変更を見送った。

- 空クエリの全件辞書を廃し、履歴パスを消費しながら復元する案は2通り実装して比較した。
  後述のとおり20・500件で遅くなったため、元の辞書方式へ戻した。優先順位を固定するテストは残した。
- ShortcutDisplayFormatterの大きなswitchはキーコードと表示記号の対応表であり、
  分岐数だけを理由に分割しても仕様の読み取りが容易にならないため維持した。
- AppCoordinatorの再読込とCacheBootstrapのスキャンには、失敗時の履歴保護、保存と通知の順序、
  再実行要求の集約がある。今回、その契約を改善できる変更の根拠は見つからず維持した。
- 履歴読込時の正規化・重複統合は、既存データの先頭優先や使用回数を変える移行になるため実施していない。
  通常検索の同点順序も既存仕様を保った。

Claude Opusにも方針と差分を読み取り専用で相談し、完全一致・先頭優先を保つ条件を確認した。
速度についての推測は採否の根拠にせず、以下の実測で判断した。

## 性能比較

Apple M2・24GiB、macOS 27.0.1、XcodeのSwift 6.4.2、debug（-Onone）で測定した。
配布物の最適化条件を変更したものではなく、以下の数値をreleaseや実利用データの所要時間とは扱わない。

入力は20・500・2,000件の `Application N` と、一覧全体にパスを分散した履歴50件。
履歴の日時は固定し、クエリは `app`・`application 49`・`absent`・空文字とした。
ディレクトリ・コマンドの性能は今回のベンチマークに含めていない。動作は関連する単体テストで確認した。

各ケースを5回ウォームアップし、7標本を別プロセスで3回、計21標本ずつ取得した。
予備計測ではシステム負荷による経過時間の変動が大きかったため、
同期検索のスレッドCPU時間を主指標にした。経過時間も生データに残している。

## 不具合と追加テスト

履歴JSONにcountが-2以下のエントリを入れると、保持スコアの `log2(count + 1)` がNaNになった。
その履歴を配列の途中に置いて上限を超えると、古い不正履歴が削除候補から外れ、通常の履歴が先に消える。
countが-1の場合は負の無限大になり、新しい履歴でも日時に関係なく先に消えた。

保持スコアの計算時だけcountを0以上へ収め、日時で比較できるようにした。
保存済みcountや検索の補正値を一括変更する移行は行っていない。
修正前は-2・Int.minと、記録時の退避・読込時の切り詰めを組み合わせた4ケースが失敗し、修正後は成功した。
-1と0を含む履歴の日時による削除順も、記録・読込の両方で確認した。

追加した動作テストは14ケース。履歴の先頭優先、完全一致優先、異なるパス・不一致履歴の分離、
空クエリの種別間の優先順位と重複、負の使用回数による保持順を対象とする。
任意実行のベンチマークには速度の合否判定を置いていない。
